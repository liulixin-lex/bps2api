# BPS2API 0.0.7

## Compatibility fixes

- Accept FUNCTION_CODE for a catalog function with an explicit string input parameter, including clients that wrap their raw exec tool as a function. The declared field name and exact source bytes are preserved. Nullable string source contracts are also recognized.
- Normalize a FUNCTION_CODE marker naming an exact custom tool to its raw custom input only when metadata is an empty JSON object. Reject unknown names and nonempty metadata instead of losing arguments. Reconstructed custom-tool history now uses the declared CUSTOM marker.
- Recover one exact registered tool invocation containing a data literal: quoted strings, identifier keys, JSON values and trailing commas. Do not evaluate expressions, infer a missing tool, split batches, accept duplicate literal keys or execute Office code.
- Normalize reasoning_text/summary_text and unambiguous image_url URL objects. Inline image aliases still pass the existing byte, decode and active-request admission limits and relay validation. Unsupported binary/file/audio content remains an explicit error; it is never silently dropped.
- Keep reasoning and initialization metadata within a bounded 256 KiB pre-output buffer. Production captures showed response.created and response.in_progress each carried about 95 KiB, which exhausted the previous 64 KiB buffer before text/tool output and disabled correction. Flush and permanently disarm correction at the cap.
- Extend the existing single shared correction budget to wrong transport declarations before client output. Non-streaming buffered text has not yet been delivered. Never replay after streamed text/tool dispatch, provider refusals, cancellation, or exhausted budget. Preserve the total request deadline.

## Evidence and limits

On September 27, 2026 a five-minute, group-scoped diagnostic capture found an exec function declaring input:string rejected under FUNCTION_CODE, plus raw PowerShell with no transport marker. Lifecycle metadata overflow prevented the latter from being corrected. The capture expired automatically. Inspection of database tables and application logs did not recover the original unknown content part from the earlier 400 response; that particular payload remains unverified. Do not claim all unknown content is supported or all provider failures are eliminated.

The release introduces no database migration or frontend change. Stage a fresh immutable container, verify text/function/custom/image/SSE requests, then switch new requests while retaining prior containers for active streams and image tokens. Roll back routing if canaries fail. Do not replace a binary inside an existing release container or overwrite the v0.0.6 tag.
