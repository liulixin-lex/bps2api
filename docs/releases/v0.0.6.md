# BPS2API 0.0.6

## Findings and changes

- Image admission previously reserved an active image slot before detecting an image, so a full image pool could reject text/tool traffic with 503. Decode and waiting-upload admission are now independent of retained image processing. Text and remote image URLs do not occupy the image pool. Pending uploads remain bounded.
- Inline-image detection follows the relay's JSON traversal, escaped strings, case-sensitive keys, last duplicate key and case-insensitive data URL scheme. Unrelated metadata no longer triggers image admission; malformed JSON is charged conservatively. Detection avoids building an unbounded object tree.
- Small, known-length identity bodies use size-weighted decode reservations and four decode slots by default, under the existing 512 MiB byte budget. Unknown-length/compressed bodies keep conservative reservations. Body size, read deadline, processing byte and active request limits remain enforced.
- A malformed local tool envelope, including raw source with a missing transport marker, can be regenerated once only before semantic output/tool dispatch. Raw code is never guessed, evaluated or silently reclassified. Remove hard-coded example tool names from the protocol prompt that may not exist in the client's catalog. Unknown tools, wrong transport types, ambiguous batches and already-started responses remain explicit errors.
- Explicit upstream HTTP 502/503/504 responses may be retried once before downstream output. The same attempt budget also bounds protocol regeneration. Respect valid Retry-After delays up to two seconds; longer/invalid values are not shortened to force a retry. Never replay connection failures, cancellation, 401/403/429 or partially delivered streams. Preserve valid upstream backoff headers on terminal rejection; empty routing pools receive Retry-After: 5.
- Normalize a missing/expired OAuth token cache entry to an empty cache miss at the repository boundary. Actual Redis errors remain errors. This eliminates false cache-failure warnings without hiding outages.
- Add deploy/audit-request-health.py: a read-only, UTC, single-snapshot audit of ops_error_logs, usage and configured account capacity. SQL errors fail visibly; recovered upstream incidents, HTTP failures and stream diagnostics are separated. It prints no credentials, prompts or response bodies.

## Production evidence and limits

The September 27, 2026 pre-release audit found routing 503s ending at 02:09:46 UTC while all existing accounts were disabled for scheduling or had errors. The first currently schedulable account was created at 02:21:49 UTC and first recorded usage at 02:22:46 UTC. The historical empty pool must not be misdiagnosed as an image-memory failure. Only one account currently supplies the affected pools; independent redundancy requires another valid, explicitly enabled account. Do not auto-enable revoked or intentionally disabled accounts.

Recent 403s explicitly reported model access changes from the provider. Preserve those errors and account settings; local code cannot grant upstream model permission. Recent 502s include malformed tool transports and one incomplete upstream stream. Bounded correction addresses only safe pre-output local failures. It cannot guarantee all provider/network errors disappear. One recovered upstream 503 had HTTP 200 and is not counted as a failed client request.

## Validation and rollout

1. Run admission/protocol/backoff/cache regression tests, the complete unit and integration suites, lint, frontend checks and security checks. A passing health endpoint alone is insufficient.
2. Stage the immutable 0.0.6 image on an unused loopback port with existing database/Redis/secrets. Back up deployment configuration privately. No database migration is introduced in this release.
3. Verify version, readiness and authenticated Responses text/tool round trips. Preserve GET/HEAD image token routing across old and new processes; tokens are process-local despite shared storage.
4. Validate and reload Caddy to direct new requests to the candidate, without proxy POST retries. Leave old processes running to drain active streams and serve existing image tokens for at least their 30-minute TTL after the last old request. Check real inline-image requests and public stream completion after switching.
5. Roll back routing immediately if canaries fail, keeping both processes available. Do not restart the old process or restore the database as part of ordinary image rollback.
6. Audit new production windows and report actual observations and remaining provider failures. A short clean window is not a guarantee of zero errors.

Recommended production guard: opt in to a 300-second upstream byte-idle timeout, with total and first-output limits left disabled for long reasoning. Heartbeats/upstream bytes reset idle accounting. Validate this against legitimate workloads rather than adding a short overall deadline.

Usage: run python3 deploy/audit-request-health.py --minutes 60 on the Docker host. Compare equivalent windows and actual traffic volume; never turn an empty/failed SQL query into a claim of no errors.
